# ARCHITECTURE.md — Архитектура UVOS: компоненты и связи

Статус: проектный документ. UVOS ни разу не собиралась; всё ниже описано
в проектном времени — «проектируется/спроектировано», а не «работает».

Целевое устройство: Xiaomi Redmi Note 13 4G NFC (`sapphire`/`sapphiren`),
Snapdragon 685 (SM6225), ядро Linux 5.15 (msm-5.15). База сборки —
LineageOS-совместимый проект, ветка lineage-22.2.

Связанные документы: [`LIMITERS.md`](LIMITERS.md) (слои исполнения, 13
каналов, политика отказа), [`CONTROL-SCHEME.md`](CONTROL-SCHEME.md) (роли,
щиток, профили), [`DESIGN.md`](../DESIGN.md), [`REQUIREMENTS.md`](../REQUIREMENTS.md),
[`PROTOTYPE.md`](PROTOTYPE.md).

## 1. Обзор

UVOS — проектируемая Android-совместимая прошивка, построенная как
«закрытая территория»: приложение по умолчанию не получает никаких данных
об устройстве и пользователе — ни времени, ни заряда, ни сети, ни
идентификаторов. Каждая выдача данных — явное решение владельца с экрана
«Контрольный щиток» (Permission Shield). Компонентов немного: оболочка-
лаунчер с приборами, щиток для правки правил, сервис ограничителей,
который их хранит и исполняет, регулятор сети, журнал попыток, модуль
профилей. Управляет всем владелец с щитка; приложения — объекты правил,
а не участники управления (роли — CONTROL-SCHEME.md §1).

## 2. Компоненты

Термин «канал данных» — вид информации, которую приложение может запросить:
время, заряд, контакты, датчики и т.д. (13 каналов — LIMITERS.md §3).

### 2a. Приборная панель (лаунчер-оболочка)

- **Назначение:** главный экран устройства и точка входа управления:
  приборы GaugeView (заряд, температура, нагрузка), статус профиля,
  счётчик попыток за сутки, кнопка входа в щиток.
- **Где живёт:** слой приложений — как системный лаунчер (HOME) в составе
  прошивки; в прототипе — обычное приложение `uvos-dashboard`.
- **Чем управляет:** ничем напрямую — это дисплей и навигация (щиток,
  профили, журнал). Право менять правила — только у щитка.

### 2b. Контрольный щиток (Permission Shield)

- **Назначение:** экран, где для каждого приложения и каждого из 13
  каналов задан режим: закрыто / огрублённо / открыто. Индикация —
  лампочки (горит/не горит, без миганий); отзыв открытого канала
  подтверждается диалогом.
- **Где живёт:** слой приложений, процесс приборной панели (отдельная
  активность); на этапе прошивки встраивается в системные настройки (D/E).
- **Чем управляет:** правилами — единственное место, где владелец меняет
  политику; каждое изменение щиток передаёт сервису ограничителей.

### 2c. Сервис ограничителей

- **Назначение:** центральный компонент. Хранит локальную базу правил
  (какое приложение какой канал в каком режиме получает) и применяет их:
  отдать всё, огрубить, вернуть «пустое» значение или отказ (политика
  отказа — LIMITERS.md §4).
- **Где живёт:** слой фреймворка — системный сервис, общий для всей
  системы; в прототипе — библиотека внутри приложения-щитка (к чужим
  приложениям правила не применяются, см. §6).
- **Чем управляет:** исполнением правил каналов 1–2 и 4–13 (время,
  батарея, геолокация, камера, микрофон, контакты, СМС, звонки, файлы,
  датчики, идентификаторы, список приложений); сеть — отдельно (2d).
  Каждую попытку к закрытому каналу фиксирует в журнале.

### 2d. Регулятор сети

- **Назначение:** отдельный ограничитель канала «Сеть». Три режима:
  полностью закрыто (по умолчанию) / белый список доменов / открыто;
  плюс лимиты трафика и расписание окон доступа (LIMITERS.md §5).
- **Где живёт:** в прошивке — ядро (netfilter, правила per-app по UID);
  в прототипе — VPN-сервис (покрывает не весь системный трафик —
  **требует проверки**).
- **Чем управляет:** сетевым доступом каждого приложения. Правила читает
  из базы правил сервиса ограничителей; обрывы и превышения лимитов
  пишет в журнал попыток.

### 2e. Журнал попыток

- **Назначение:** хронология обращений к закрытым каналам: время,
  приложение, канал, результат (выдано/огрублено/отказано), без
  содержимого данных. Просмотр — статичный список; у новых записей
  статичная красная точка (#E02020), без миганий.
- **Где живёт:** слой приложений (экран чтения) + слой фреймворка (запись
  событий сервисом ограничителей). Хранение — локально, в защищённом
  хранилище UVOS.
- **Чем управляет:** ничем — журнал только пишет и показывает. Отключить
  его нельзя.

### 2f. Модуль профилей

- **Назначение:** именованные наборы состояний каналов: «Стерильно»
  (всё закрыто, эталон по умолчанию), «Связь» (звонки и СМС открыты
  владельцу, приложениям — нет), «Своя настройка». Переключение —
  мгновенно, с записью в журнал правил.
- **Где живёт:** слой фреймворка рядом с сервисом ограничителей (модуль
  над той же базой правил); в прототипе — элемент главного экрана.
- **Чем управляет:** массовым применением правил. Профиль не создаёт
  собственных решений — он переписывает содержимое базы правил целиком.

### 2g. Системные сервисы Android (патчи)

- **Назначение:** стандартные сервисы AOSP, которые придётся патчить.
  Время и заряд приложения читают без всяких разрешений, поэтому закрыть
  их можно только в самих сервисах (LIMITERS.md §2.2, §3): сервис времени
  (огрубление до часа/минуты/точно) и сервис батареи (фиксированное/
  нулевое значение). Позднее — датчики, идентификаторы, PackageManager,
  провайдеры (контакты, СМС, звонки, файлы).
- **Где живёт:** слой фреймворка lineage-22.2 (этап D/E).
- **Чем управляет:** выдачей данных по своим каналам. Точный набор
  точек перехвата в lineage-22.2 — **требует проверки** по исходникам.

## 4. Потоки данных

### 4.1. Приложение читает время

1. Приложение вызывает системный API времени.
2. Сервис ограничителей сверяет базу правил: канал «Время» закрыт/огрублён.
3. Патч сервиса времени подменяет ответ: огрублённое значение
   (час/минута) или отказ по политике отказа (LIMITERS.md §4).
4. Попытка — в журнал; счётчик на панели растёт; приложение ничего не узнаёт.

### 4.2. Приложение открывает сеть

1. Приложение пытается установить сетевое соединение.
2. Регулятор сети сверяет базу правил: «закрыто» (по умолчанию) или
   белый список.
3. В прошивке пакеты отсекает фильтр ядра (per-app по UID); в прототипе
   то же делает VPN-сервис приложения-щитка.
4. Соединение не устанавливается; факт попытки/обрыва — в журнал;
   причина приложению не сообщается.

### 4.3. Владелец меняет профиль

1. Владелец открывает «Профили» на панели и выбирает, например, «Связь».
2. Модуль профилей переписывает базу правил: звонки и СМС открыты
   владельцу, все приложения — вне территории.
3. Сервис ограничителей применяет правила мгновенно, без перезагрузки;
   регулятор сети синхронизирует канал «Сеть».
4. Переключение — в журнал правил; панель обновляет статус профиля.

## 5. Хранение правил

- **Где:** локальная база правил на устройстве, в защищённом хранилище
  UVOS, недоступном обычным приложениям. **Без облака, без аккаунтов,
  без синхронизации** (CONTROL-SCHEME.md §6).
- **Формат:** именованные записи «приложение × канал × режим», параметры
  сети (режим, белый список, лимиты, расписание) и профили. В прототипе —
  простой сериализованный файл во внутренней памяти; формат для прошивки
  уточняется — **требует проверки**.
- **Журналирование:** при каждом изменении правил (канал, сеть, профиль)
  сервис ограничителей дописывает запись в журнал правил: что изменено,
  когда, с какого значения на какое (менять правила может только
  владелец). Журнал правил и журнал попыток — отдельные списки; оба
  отключить нельзя.
- **Отказоустойчивость:** база правил переживает перезагрузку; её
  повреждение обрабатывается безопасным режимом (CONTROL-SCHEME.md §5).

## 6. Связь с прототипом

Прототип `uvos-dashboard` — Kotlin-приложение без зависимостей, этап C;
на щитке есть плашка «ДЕМО» (честная маркировка).

- **Уже есть (UI-элементы):** приборы GaugeView (BATT, TEMP; стрелка
  с инерцией ~600 мс), лампочки каналов на щитке (ShieldActivity),
  шапка-прибор «ACCESS», кнопка входа в щиток, палитра UVOS.
- **Появится (этап C):** регулятор сети как VPN-сервис, журнал попыток
  (статичные красные точки), профили «Стерильно/Связь», диалог
  подтверждения отзыва канала, локальная база правил вместо памяти экрана.
- **Прототип НЕ делает:** не ограничивает другие приложения (нужны правки
  фреймворка — этап D/E), не закрывает время и заряд (платформа отдаёт
  их без разрешений), не читает ничего сверх броадкаста батареи, сеть
  не использует вовсе.

## 7. Этапность

- **Этап C — прототип-приложение:** приборная панель, щиток, регулятор
  сети (VPN-сервис), журнал попыток, профили, локальная база правил.
  Логика ограничений внутри одного приложения; изоляция чужих — нет.
- **Этап D/E — правки фреймворка (lineage-22.2):** сервис ограничителей
  как системный сервис, патчи времени и батареи (затем датчики,
  идентификаторы, PackageManager, провайдеры), щиток в системных
  настройках, защищённое хранилище правил. Нужна пересборка прошивки.
- **Этап F+ — правки ядра (msm-5.15):** регулятор сети переносится из
  VPN-сервиса в netfilter (per-app по UID); LSM-хуки как последний
  рубеж. Отдельная цепочка тестов.

Порядок фиксирован: логика (C) → фреймворк (D/E) → ядро (F+); каждый
этап проверяется тестами перед следующим (LIMITERS.md §8).
