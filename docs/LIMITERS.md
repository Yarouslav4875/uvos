# Работа ограничителей: как UVOS прячет данные от приложений

Проект: UnderVoltOS (UVOS)
Статус: концепция. Прошивка ни разу не собрана; документ описывает план,
а не готовую систему.
Целевое устройство: Xiaomi Redmi Note 13 4G NFC (23124RA7EO), кодовое имя
`sapphire`/`sapphiren`, Snapdragon 685 (SM6225), ядро Linux 5.15
(Android common kernel msm-5.15). База сборки — LineageOS-совместимый
проект, ветка lineage-22.2.

UVOS исходит из простого принципа: приложение по умолчанию не получает
НИКАКИХ данных об устройстве и пользователе — ни времени, ни заряда, ни
идентификаторов, ни файлов, ни сети. Каждая выдача данных — явное решение
пользователя на экране «Контрольный щиток» (Permission Shield).

---

## 1. Термины

- **Канал данных** — любой способ, которым приложение может узнать
  что-то о системе или пользователе. Примеры: чтение текущего времени,
  запрос уровня батареи, доступ к контактам, открытие сетевого
  соединения. Каналов много, и не все очевидны.
- **Ограничитель** — код, который стоит на пути канала данных и решает,
  что отдать приложению: всё, огрублённое значение, ноль или ошибку.
  Ограничитель не «шпионит» — он фильтрует ответы системы приложению.
- **Щиток** (Permission Shield) — экран управления UVOS, где для каждого
  приложения и каждого канала задан режим: закрыто / огрублённо /
  открыто. Это единственное место, где пользователь меняет политику.
- **Слой исполнения** — уровень системы, где выполняется код и где
  физически можно поставить ограничитель. Три слоя: приложения,
  фреймворк (AOSP), ядро Linux. Подробнее — раздел 2.
- **Политика отказа** — что именно приложение получает, когда
  ограничитель закрыл канал (см. раздел 4).

---

## 2. Три слоя исполнения

Ограничители живут не «где-то вообще», а в конкретных слоях. Чем глубже
слой, тем больше он контролирует — но тем дороже его править.

### 2.1. Слой приложений (обычное Android-приложение)

- **Что видит:** только своё окружение: свои файлы, свои разрешения,
  результаты системных вызовов через API Android.
- **Что может контролировать:** без root и без правок системы доступно
  немногое:
  - не запрашивать и не объявлять опасные разрешения в манифесте
    (`manifest` — декларация приложения);
  - работать через AppOps — встроенный механизм Android, который
    позволяет дополнительно гасить операции даже «тихих» разрешений.
- **Пределы слоя:** приложение не может перехватить чужие приложения,
  системные сервисы или сеть целиком. И главное: время и заряд батареи
  Android-приложения могут читать **без всяких разрешений** — на этом
  слое их не закрыть. Это честное ограничение платформы, обойти его
  можно только правками фреймворка.

### 2.2. Слой фреймворка (AOSP / LineageOS)

Фреймворк — это Java/Kotlin-код между приложениями и ядром: системные
сервисы, менеджер разрешений, реализации API.

- **Что видит:** все запросы приложений к системным сервисам.
- **Что может контролировать:** ответы этих сервисов. Здесь ставятся
  ограничители на время, батарею, датчики, идентификаторы, список
  приложений, доступ к файлам через API.
- **Пределы слоя:** фреймворк не видит «сырой» сетевой трафик приложения
  и не может гарантированно спрятать то, что выдаёт само ядро. Требует
  правок дерева device/vendor и пересборки прошивки — на текущем ПК
  (16 ГБ ОЗУ, ~164 ГБ диска) полная сборка AOSP невозможна, этап
  переносится на другую машину.

### 2.3. Слой ядра (Linux 5.15, msm-5.15)

- **Что видит:** всё: сетевые пакеты, файловые операции, системные
  вызовы.
- **Что может контролировать:**
  - **сетевой фильтр per-app** — фильтрация трафика отдельно для каждого
    приложения (по UID: Linux-идентификатор пользователя/процесса);
  - **LSM-хуки** — точки перехвата в ядре (Linux Security Modules), где
    можно проверять каждую операцию и запрещать её.
- **Пределы слоя:** правки ядра сложны в поддержке и требуют пересборки
  ядра под целевое устройство. В UVOS ядро — последний рубеж, а не
  первый инструмент.

Таблица основных каналов. «Слой» — где реализуется ограничитель;

## 4. Что видит приложение при блокировке

Политика отказа UVOS: **не крэшить, не предупреждать, не выдавать факт
блокировки.**

- **Пустые и нулевые значения вместо ошибок.** Там, где это возможно,
  ограничитель возвращает законный «пустой» ответ: пустой список
  контактов, нулевой уровень батареи, отсутствие датчика в перечне.
  Приложение получает валидный ответ API — просто без данных.
- **Ошибки — только там, где иначе нельзя.** Камеру «нулевым значением»
  не спрячешь: если канал закрыт, открытие камеры завершается ошибкой,
  как если бы устройство отсутствовало.
- **Огрубление времени — промежуточный режим.** Полностью спрятать время
  на слое приложений нельзя, но можно выдавать его с точностью до часа
  или минуты. Это компромисс: приложениям-будильникам время всё же
  нужно. Щиток позволяет выбрать точность: час / минута / точно.
- **Молчание вместо предупреждения.** Приложение не получает уведомления
  «доступ запрещён» от системы и не видит записи о блокировке в своих
  логах. Иначе оно могло бы по косвенным признакам «прощупать» систему:
  заметить, что ответ отличается от обычного Android, и сделать выводы
  об окружении пользователя.

Цель — чтобы заблокированный канал выглядел для приложения как пустое
устройство или как обычный Android с «очень скучными» данными, а не как
надзор.

## 5. Сеть как отдельный ограничитель

Сеть в UVOS — не разрешение, а отдельный ограничитель с тремя режимами:

1. **Полностью закрыто** (по умолчанию). Приложение не имеет сетевого
   доступа ни в каком виде.
2. **Белый список доменов.** Приложению разрешены только явно указанные
   адреса/домены. Всё остальное отсекается.
3. **Открыто.** Полный доступ, при желании с лимитами (объём трафика в
   сутки) и расписанием (например, только в заданные часы).

Дополнительно к режиму: **лимиты** (квота трафика) и **расписание**
(окна доступа).

- **Этап прототипа:** ограничитель реализуется как VPN-сервис внутри
  приложения-прототипа. Android даёт обычному приложению право поднять
  VPN-интерфейс (с согласия пользователя) и фильтровать весь трафик.
  Это работает без root, но покрывает не всё: некоторые соединения
  (например, часть системного трафика) могут идти мимо VPN —
  **требует проверки**.
- **Этап прошивки:** ограничитель переносится в ядро: netfilter
  (подсистема фильтрации пакетов) с правилами per-app по UID и
  iproute (управление маршрутами). На этом слое фильтрация честнее и
  не зависит от того, стартовал ли VPN-интерфейс.

## 6. Журнал попыток

Каждое обращение к ограниченному каналу фиксируется:

- **Что логируем:** время события, имя приложения, канал (какой из
  13), результат (выдано / огрублено / отказано). Без содержимого
  данных — только сам факт обращения.
- **Где хранится:** локально на устройстве, в защищённом хранилище
  UVOS, недоступном обычным приложениям. На этапе прототипа — во
  внутренней памяти приложения-щитка.
- **Кто читает:** только пользователь, через экран щитка. Журнал не
  отправляется никуда и не синхронизируется. Просмотр журнала —
  статичный список, без миганий и цветовой тревоги: обычные строки
  текста.
- **Ограничение:** журнал сам по себе не гарантирует полноту — часть
  побочных каналов (раздел 7) не проходит через ограничители и в
  журнал не попадает.

## 7. Чего ограничитель НЕ может

Честный список пределов концепции. Это не «доработаем потом», а
фундаментальные ограничения.

- **Побочные каналы.** Приложение может оценивать окружение по времени
  ответа системы, размеру экрана, производительности, количеству ядер.
  Это не «каналы данных» в явном смысле, и полностью их не закрыть.
- **Sideload APK.** Приложение, установленное вручную мимо щитка
  (например, через браузер или USB), до интеграции щитка в сборку
  получит стандартные разрешения Android и не будет ограничено. Полный
  контроль возможен только в собранной прошивке.
- **Время и заряд без правок фреймворка.** На этапе прототипа
  (обычное приложение без root) время и заряд закрыть нельзя — платформа
  отдаёт их без разрешений.
- **Косвенный анализ пустых значений.** Приложение может заметить, что
  контактов всегда ноль и сеть всегда закрыта, и сделать вывод о
  «странном устройстве». Мы не выдаём факт блокировки напрямую, но
  устойчивое отсутствие данных — само по себе сигнал.
- **Системные приложения и чужой код.** Ограничители управляют тем,
  что проходит через контролируемые точки. Поведение вендорских служб
  Xiaomi/Qualcomm вне фреймворка — **требует проверки**; возможно,
  часть из них придётся отключать отдельно.
- **Аппаратные утечки.** Например, радио-модули (Wi-Fi, Bluetooth,
  сотовая связь) работают на уровне ниже фреймворка; их состояние
  может быть видно производителю оборудования даже при закрытом
  сетевом канале приложений.

## 8. Этапность внедрения

Без инструкций по прошивке и разблокировке загрузчика — только порядок
работы над кодом.

### Этап C — прототип-приложение (всё, что доступно без root)

- Каркас щитка: экран управления режимами каналов, хранение политик.
- VPN-сервис как сетевой ограничитель (три режима, лимиты, расписание).
- Журнал попыток.
- AppOps-подавление опасных разрешений там, где прототип их запрашивает.
- Границы этапа: время, заряд, идентификаторы, список приложений —
  не закрываются. Это прототип логики, а не изоляции.

### Этап D/E — правки фреймворка LineageOS (lineage-22.2)

- Ограничители в системных сервисах: время, батарея, датчики,
  идентификаторы, PackageManager, провайдеры (контакты, СМС, звонки,
  файлы).
- Интеграция щитка в системные настройки прошивки.
- Требуется: деревья device/vendor/kernel, пересборка прошивки на
  машине с достаточными ресурсами (текущий ПК 16 ГБ ОЗУ / ~164 ГБ диска
  сборку не тянет).

### Этап F+ — правки ядра Linux 5.15 (msm-5.15)

- Сетевой фильтр per-app по UID в netfilter; перенос политики сети
  из VPN-сервиса в ядро.
- LSM-хуки как последний рубеж для файловой системы и системных
  вызовов.
- Требуется: пересборка ядра под sapphire/sapphiren, отдельная цепочка
  тестов. Никаких действий с реальным устройством на этом этапе
  не планируется без готовой сборки.

Порядок этапов фиксирован: логика (C) → фреймворк (D/E) → ядро (F+).
Каждый этап проверяется отдельно, на документированных тестах, прежде
чем следующий начнётся.
