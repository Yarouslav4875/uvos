# SECURITY-AUDIT.md — Аудит безопасности UVOS и анализ лазеек перехвата контроля

Статус: проектный документ. Фиксирует результаты первичного аудита безопасности
структуры UnderVoltOS (UVOS), соответствие минимальным стандартам безопасности ОС
(AOSP CDD, NIST SP 800-163/218) и перечень теоретических лазеек несанкционированного
перехвата контроля над устройством.

Связанные документы: [`ARCHITECTURE.md`](ARCHITECTURE.md), [`LIMITERS.md`](LIMITERS.md),
[`CONTROL-SCHEME.md`](CONTROL-SCHEME.md), [`TEST-CHECKLIST.md`](TEST-CHECKLIST.md).

---

## 1. Резюме текущего состояния структуры

На текущем этапе UVOS реализуется по гибридной схеме:
1. **Прототип-интерфейс (`uvos-dashboard`):** Kotlin-приложение лаунчера и контрольного щитка.
2. **Конвейер интеграции (`run-pipeline.ps1`, `repack-step.ps1`):** скрипт распаковки
   базового образа LineageOS 22.2 (`system.img`), инъекция `UVOSDashboard.apk`
   в каталог `/system/priv-app/` и упаковка в EROFS.

> [!WARNING]
> **Критическое разграничение:** Текущая инъекция APK в `/system/priv-app/` **НЕ изолирует**
> сторонние приложения. На уровне сборки без модификации фреймворка и ядра любое
> установленное приложение исполняется со стандартными правами Android и обходит щиток
> напрямую. Полная безопасность достигается только на этапах D/E (фреймворк) и F (ядро).

## 2. Соответствие минимальным стандартам безопасности ОС

| Стандарт / Механизм | Минимальное требование безопасности | Состояние в UVOS | Риск / Оценка |
|---|---|---|---|
| **Root of Trust & AVB 2.0** | Криптографическая проверка разделов (`boot`, `system`, `vendor`) через `dm-verity` и открытый ключ в Keystore. | Перепаковка `system.img` ломает дерево хешей `vbmeta`. При отключении verity целостность ФС не гарантируется. | **КРИТИЧЕСКИЙ**: доступ к блочному устройству позволяет внедрить персистентный руткит. |
| **SELinux (MAC)** | Принудительный режим (**Enforcing**), изолированные домены для всех компонентов, запрет permissive-переходов. | Добавлен только базовый контекст `u:object_r:system_file:s0` для APK. Требуется строгий аудит политик базового ROM. | **ВЫСОКИЙ**: если базовый ROM собран с `Permissive`, вся изоляция Android не работает. |
| **Фильтрация системных вызовов (seccomp-bpf)** | Белый список syscalls для Zygote и непривилегированных процессов. Блокировка прямых запросов к ядру. | Стандартный seccomp Android. Нет перехвата syscalls времени (`clock_gettime`) и прямого доступа к сокетам. | **ВЫСОКИЙ**: приложения на C/C++ (NDK) обходят Java-ограничители. |
| **Шифрование данных (FBE)** | Аппаратное шифрование File-Based Encryption с защитой ключей в Qualcomm TEE (TrustZone). | Зависит от вендорских блобов Redmi Note 13 4G (sapphire). | **СРЕДНИЙ**: требует сохранения совместимости с Keymint HAL. |
| **Изоляция IPC (Binder)** | Проверка прав и UID вызывающего (`Binder.getCallingUid()`) на каждом интерфейсе сервисов. | Сервис правил пока находится внутри APK; при выносе в системный сервис потребуется строгая защита подписью. | **ВЫСОКИЙ**: риск несанкционированного изменения правил сторонними приложениями. |

## 3. Теоретические лазейки несанкционированного перехвата контроля

Ниже приведен детальный разбор векторов атак, через которые злоумышленник
или вредоносное ПО может обойти концепцию «закрытой территории» и перехватить контроль.

### 3.1. Вектор поставки (Supply Chain): Неверифицированная база ROM
- **Уязвимость:** Скрипт `run-pipeline.ps1` скачивает неофициальную сборку со стороннего ресурса, сверяя только размер файла (`Length -ge $targetLength`).
- **Механика атаки:** При компрометации зеркала или атаке типа «человек посередине» (MITM) загружается поддельный образ с предустановленным бэкдором, модифицированным `adbd` или уязвимым ядром.
- **Последствия:** Полный удаленный контроль над устройством до первого запуска оболочки UVOS.
- **Требование защиты:** Обязательная сверка SHA-256 хеша и валидация открытым ключом автора сборки.

### 3.2. Обход Java-ограничителей через нативный код (NDK / Syscalls / Sysfs)
- **Уязвимость:** Ограничение каналов только на уровне Java-фреймворка (TimeService, BatteryService).
- **Механика атаки:**
  - Приложение на C/C++ вызывает `clock_gettime(CLOCK_REALTIME)` напрямую через vDSO / syscall ядра Linux, полностью игнорируя Java API времени.
  - Приложение читает `/sys/class/power_supply/battery/` или `/proc/net/` напрямую через системные вызовы файловой системы.
- **Последствия:** Обход каналов времени, батареи и части сетевых идентификаторов без запроса разрешений.
- **Требование защиты:** SELinux-политики, запрещающие чтение `/sys` для домена `untrusted_app`, и seccomp-фильтрация системных вызовов времени.

### 3.3. Кликджекинг и перехват через службы доступности (Accessibility Services)
- **Уязвимость:** Вредоносное приложение со статусом службы доступности может перехватывать экранные события и эмулировать жесты.
- **Механика атаки:**
  - Приложение программно открывает экран «Контрольный щиток» (`ShieldActivity`).
  - Эмулирует нажатия по индикаторным лампочкам, переводя каналы («Сеть», «Микрофон», «Геолокация») в режим `OPEN`.
  - Автоматически подтверждает диалог отзыва/выдачи разрешений.
- **Последствия:** Скрытное снятие всех блокировок без ведома владельца.
- **Требование защиты:**
  - Защита окон управления флагом `WindowManager.LayoutParams.FLAG_SECURE`.
  - Запрет взаимодействия Accessibility-сервисов с пакетом `com.uvos.dashboard` на уровне фреймворка.
  - Подтверждение критических изменений биометрией или системным PIN-кодом.

### 3.4. Утечки сетевого регулятора (VPN vs Netfilter)
- **Уязвимость:** Реализация регулятора сети через Android `VpnService` на этапе прототипа.
- **Механика атаки:**
  - Системные службы с UID < 10000 могут направлять трафик в обход VPN-туннеля.
  - В момент падения, перезапуска сервиса или смены сети возможна кратковременная утечка пакетов (leak).
  - Утечка DNS через IPv6-интерфейсы.
- **Последствия:** Несанкционированная передача телеметрии или соединение с командным сервером.
- **Требование защиты:** Использование сетевого фильтра ядра (netfilter/eBPF cgroup) с политикой по умолчанию `DROP` для всех непривилегированных UID.

### 3.5. Отладочные свойства сборки (Debug Properties и adbd)
- **Уязвимость:** Неофициальные прошивки часто собираются с отладочными флагами (`ro.debuggable=1`, `ro.secure=0`).
- **Механика атаки:**
  - `ro.debuggable=1` позволяет подключить отладчик JDWP к любому процессу в системе и выполнить произвольный код.
  - `adbd` без обязательной RSA-авторизации позволяет получить shell через USB или локальный Wi-Fi порт 5555.
- **Последствия:** Неавторизованный shell-доступ и повышение привилегий до `system`/`root`.
- **Требование защиты:** Конфигурация исключительно релизного типа: `ro.build.type=user`, `ro.debuggable=0`, `ro.secure=1`, `ro.adb.secure=1`.

## 4. Архитектурный план закрытия уязвимостей (Hardening Roadmap)

1. **Этап C (Прототип):**
   - Добавить контрольную сумму SHA-256 в скрипт `run-pipeline.ps1`.
   - Включить `FLAG_SECURE` во всех окнах настроек щитка `UVOSDashboard`.
   - Обеспечить строгую проверку `android:exported="false"` для внутренних компонентов.

2. **Этап D/E (Фреймворк LineageOS):**
   - Реализовать `RuleService` как системный сервис с проверкой `Binder.getCallingUid()`.
   - Выдавать доступ к сервису правил только приложениям, подписанным системным ключом платформы (`platform.pk8`).
   - Изолировать системные вызовы времени и сенсоров через seccomp.
   - Исключить доступ Accessibility-сервисов к экранам щитка.

3. **Этап F (Ядро Linux 5.15):**
   - Перенести блокировку сети в netfilter / eBPF (per-UID drop).
   - Заблокировать чтение сырых аппаратных интерфейсов `/sys/class/power_supply` непривилегированными процессами через SELinux.
   - Восстановить целостность AVB 2.0 с внедрением собственного ключа подписи (`avb_custom_key`).
