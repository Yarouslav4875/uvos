# CONTROL-SCHEME.md — Схема управления UVOS: кто и как управляет системой

Статус: проектный документ (дизайн, не реализованная система). UVOS пока не
собиралась ни разу — существует только прототип-приложение `uvos-dashboard`
(Kotlin, без зависимостей). Всё ниже описано в проектном времени:
«планируется/спроектировано», а не «работает».

Связанные документы: [`REQUIREMENTS.md`](../REQUIREMENTS.md) (концепция
«закрытой территории»), [`DESIGN.md`](../DESIGN.md) (стиль элементов),
[`LIMITERS.md`](LIMITERS.md) (как ограничения исполняются технически).

**Термины** (объясняем при первом использовании):
- **Канал данных** — именованный вид информации, который приложение может
  запросить: время, заряд батареи, геолокация, контакты, датчики и т.д.
  Канал «Сеть» — особый: это не данные, а дорога наружу, у него свой
  регулятор.
- **Владелец** — человек, физически владеющий телефоном. Один на устройство.
- **Щиток (Permission Shield)** — экран со списком каналов и индикаторными
  лампочками: горит/не горит = канал открыт/закрыт.
- **Профиль ограничений** — именованный набор состояний каналов, который
  можно переключать одним действием.

---

## 1. Роли

В системе три роли. Права распределены жёстко и не пересекаются:

| Роль | Кто это | Что может | Чего не может |
|---|---|---|---|
| **Владелец** | Человек, хозяин телефона | Менять любые правила: открывать/закрывать каналы, настраивать регулятор сети, переключать профили, читать журнал попыток | Делегировать права приложениям или другим людям (роль одна) |
| **Приложения** | Любой софт, установленный на устройстве | Просить доступ к каналу (запрос фиксируется в журнале) и пользоваться тем, что явно открыто | Менять правила, читать закрытые каналы, отключать наблюдение за собой, узнавать правила других приложений |
| **Система** | Ядро UVOS (ограничители, см. LIMITERS.md) | Исполнять правила молча и мгновенно: блокировать, подменять/огрублять данные, писать журнал | Спрашивать у приложений что-либо, «уговаривать», давать исключения без записи владельца |

Ключевой принцип ролей: **система никогда не спрашивает приложение**.
Вопрос «разрешить этому приложению доступ?» задаётся только владельцу.
Приложение — объект ограничений, а не участник управления: оно не может
ни попросить пересмотра, ни показать свой диалог «дайте доступ», как это
делает обычный Android. Любая его попытка получить данные закрытого канала —
это событие для журнала, а не повод для диалога.

## 2. Уровни управления

Управление собрано в иерархию экранов. Навигация планируется так:
с главного экрана вниз в щиток, из щитка — в регулятор сети и журнал,
профили доступны прямо с главного экрана.

```
┌─────────────────────────────────────────────┐
│ ГЛАВНЫЙ ЭКРАН (приборная панель)            │
│  приборы GaugeView, статус профиля,         │
│  счётчик попыток доступа за сутки           │
└─────────────────────────────────────────────┘
        │                              │
        │ «Щиток»                      │ «Профили»
        │                              │
        │                              └→ ┌──────────────────────┐
        │                                 │ ПРОФИЛИ ОГРАНИЧЕНИЙ  │
        │                                 │ Стерильно / Связь /  │
        │                                 │ Своя настройка       │
        │                                 └──────────────────────┘
┌───────────────────────────┐
│ ЩИТОК (Shield)            │
│ per-app каналы: лампочки  │
│ каналов                   │
└───────────────────────────┘
     │                   │
     │ «Сеть»            │ «Журнал»
     │                   │
     │                   └→ ┌──────────────────┐
     │                      │ ЖУРНАЛ ПОПЫТОК   │
     │                      │ список попыток,  │
     │                      │ красная точка у  │
     │                      │ новых записей    │
     │                      │ (статичная)      │
     │                      └──────────────────┘
     └→ ┌──────────────┐
        │ РЕГУЛЯТОР    │
        │ СЕТИ (per-   │
        │ app): режимы,│
        │ лимиты, рас- │
        │ писание      │
        └──────────────┘
```

Назначение уровней:
- **Главный экран** — обзор: приборы (стрелки с инерцией ~600 мс), текущий
  профиль, сводка по журналу. Отсюда всё остальное доступно за одно нажатие.
- **Щиток** — выбор приложения и его каналов: лампочка у каждого канала.
  Нажатие по лампе — открытие/закрытие канала.
- **Регулятор сети** — отдельный экран для канала «Сеть»: режимы
  (закрыто / белый список / открыто), лимиты трафика, расписание.
- **Журнал попыток** — хронология обращений приложений к закрытым каналам.
- **Профили** — быстрое переключение между наборами правил (раздел 4).

## 3. Потоки управления

Четыре ключевых сценария. Везде действует одно правило: жмёт только
владелец, исполняет только система, приложение узнаёт о результате лишь
по факту (данные пришли или отказ произошёл).

### 3a. Выдать разрешение канала

1. Владелец: главный экран → «Щиток» → выбирает приложение → находит
   канал (например, «Датчики») → нажимает лампочку.
2. Система: включает канал, лампочка загорается статичным светом
   (мигания запрещены, см. DESIGN.md), запись об изменении уходит в журнал
   правил.
3. Приложение: со следующего запроса получает данные канала. Никакого
   уведомления ему не показывается — изменение «в моменте», как щелчок
   тумблера.

### 3b. Отозвать уже открытый канал

1. Владелец: там же нажимает горящую лампочку открытого канала.
2. Система: показывает диалог подтверждения (отзыв действующего доступа —
   опасное действие, его подтверждает владелец; см. раздел 6). После
   подтверждения канал закрывается **мгновенно**: уже выданные данные
   не «доигрывают», следующий запрос получает отказ.
3. Приложение: начинает получать отказ по закрытому каналу. Держать
   сессию/кэш на выданном ранее — его проблема, система забирать данные
   обратно не может (честный предел, см. LIMITERS.md).

### 3c. Приложение обращается к закрытому каналу

1. Приложение: вызывает API закрытого канала (например, читает точное
   время).
2. Система: отказывает (политика отказа — в LIMITERS.md) и записывает
   попытку в журнал: приложение, канал, время, действие.
3. Владелец: на главном экране растёт счётчик попыток; в журнале у новых
   записей появляется **статичная красная точка** (#E02020) — метка
   «не просмотрено». Точка не мигает; она гаснет, когда запись просмотрена.
4. Приложение: видит только отказ. О том, что попытка записана, оно не
   знает.

### 3d. Приложение выходит за сетевой лимит

1. Приложение: тратит трафика больше, чем разрешено регулятором сети
   (лимит задан владельцем: за день/час, по объёму).
2. Система: обрывает сеть для этого приложения (остальные — по их правилам),
   пишет в журнал: «лимит превышен, сеть отрезана».
3. Владелец: видит запись в журнале (с красной точкой) и состояние канала
   «Сеть» на регуляторе — режим, лимит, факт обрыва.
4. Приложение: сеть недоступна до конца периода лимита или до вмешательства
   владельца. Автоматического «прощения» нет.

## 4. Профили ограничений

Профиль — именованный набор состояний каналов. Переключение доступно
прямо с главного экрана и применяется мгновенно, с записью в журнал
(что переключено, с какого профиля на какой, когда).

| Профиль | Смысл | Каналы |
|---|---|---|
| **«Стерильно»** | Профиль по умолчанию. Новое устройство и любое «не знаю, что делать» | Всё закрыто: приложения не видят ни времени, ни заряда, ни датчиков, ни сети |
| **«Связь»** | Телефон должен звонить и принимать СМС, но приложения — по-прежнему вне территории | Звонки и СМС открыты на уровне владельца (он пользуется телефоном как телефоном); всем приложениям эти каналы и всё остальное закрыты |
| **«Своя настройка»** | Ручной набор: владелец открыл часть каналов через щиток | Текущее состояние щитка и регулятора сети, сохраняется как именованный профиль |

Правила переключения:
- действует мгновенно, без перезагрузки и «перезапуска приложений»;
- каждое переключение журналируется (в журнал правил, не в журнал попыток);
- «Стерильно» нельзя отредактировать — это эталон «всё закрыто», к которому
  всегда можно вернуться одним нажатием.

## 5. Экстренные случаи

Случай: лаунчер или щиток повреждены (сбой обновления, повреждение файлов,
ошибка сборки). Управление системой не должно зависеть от одного экрана.

**Что проектируется:** безопасная загрузка. При повреждении основного
интерфейса устройство загружается в урезанный режим, где открытым остаётся
только щиток: владелец может посмотреть правила, закрыть/открыть каналы и
переключиться в «Стерильно». Данные владельца при этом не трогаются —
режим касается только интерфейса управления, не стирания и не сброса.

**Как это реализуется:**
- на этапе прошивки — через механизм восстановления (recovery) базовой
  основы: планируется использовать встроенный режим восстановления
  LineageOS как точку входа в безопасный режим. Конкретный механизм
  (как именно подменять/ограничивать интерфейс, какие пункты recovery
  показывать) — **требует проверки** по документации LineageOS recovery
  для sapphire/sapphiren;
- на этапе прототипа (`uvos-dashboard` — обычное APK-приложение) — простое
  решение: повреждённый APK переустанавливается заново. Данные прототипа
  хранить в нём не планируется, поэтому переустановка ничего не теряет.

**Правило экстренного режима:** в нём нельзя удалить данные, изменить
роли или выключить журнал. Меньше прав — меньше цена ошибки.

## 6. Принципы управления

1. **Всё локально.** Ни облака, ни аккаунтов, ни телеметрии. Правила живут
   на устройстве; управление работает без связи с внешним миром.
2. **Опасные действия подтверждает владелец.** Отзыв действующего доступа
   (3b) и переключение профиля, закрывающий открытые каналы, — через диалог
   подтверждения. Открытие канала подтверждения не требует: владелец и так
   сознательно нажал тумблер.
3. **Система никогда не спрашивает приложение.** Ни разрешения, ни
   подтверждения, ни объяснений. Приложение — объект правил, не субъект.
4. **Изменения правил журналируются.** Каждое действие владельца (канал,
   сеть, профиль) попадает в журнал правил. Журнал попыток — отдельный,
   только для обращений приложений. Журналы нельзя отключить.
5. **Управление не зависит от сети.** Щиток, профили, журнал открываются
   и меняют правила при полностью выключенной сети. Сбой канала «Сеть»
   не может заблокировать владельцу доступ к управлению.
6. **Статичность индикации.** Все индикаторы (лампочки каналов, красная
   точка в журнале) — статичные, без миганий: мигание это движение, а
   движение в UVOS допускается только в приборах (инерция стрелки ~600 мс).
