# ARCHUVOS-BACKGROUND.md — Архитектура фонового стека ArchUVOS

**Версия:** 1.0 (Arch Linux Rolling Baseline)  
**Статус:** Проектная спецификация фоновой архитектуры (Background / Core Engine)  
**Назначение:** Полное техническое описание демонов, модулей ядра, изоляции «Закрытой территории», сетевого регулятора и аппаратного модуля питания для реализации ArchUVOS на базе Arch Linux.

---

## 1. Введение и концепция фонового слоя

В классическом дистрибутиве Arch Linux фоновые процессы не имеют единого координирующего центра безопасности: каждое пользовательское приложение наследует полные привилегии текущего пользователя, имеет открытый доступ к сети, аппаратным сенсорам, файловой системе и системным таймерам высокого разрешения.

**ArchUVOS Background** коренным образом меняет парадигму операционной системы:
1. **Zero-Trust Capsule (Нулевое доверие к приложениям):** Любое приложение пользователя по умолчанию запускается в изолированной капсуле (Sandbox), лишённой сети, доступа к чужим файлам, идентификаторам машины и точным системным часам.
2. **Deterministic Governance (Детерминированное управление):** Доступ к ресурсам выдаётся только владельцем через аппаратный переключатель (тумблер) на Контрольном щитке (Permission Shield).
3. **UnderVolt Core & Hardware Telemetry:** Фоновый аппаратный демон контролирует смещения напряжения процессора (CPU Voltage Offset), кривые GPU и лимиты мощности (RAPL Package Power Limit), транслируя телеметрию в реальном времени на аналоговые приборы М4200.
4. **Служебный минимализм:** Отсутствие тяжелых фреймворков. Все фоновые демоны пишутся на чистом **Rust** или **C++20**, потребляют суммарно < 35 МБ оперативной памяти и не создают паразитной нагрузки на CPU.

## 3. Компоненты фонового слоя

### 3.1 `archuvos-cored` (Главный системный супервизор)

- **Тип:** Системный демон `systemd` (`archuvos-core.service`), запускается с привилегиями `root`.
- **Язык разработки:** Rust (async-std / zbus / sqlite3).
- **Зона ответственности:**
  - Управление состоянием безопасности дистрибутива.
  - Обработка вызовов по системной шине D-Bus (`org.archuvos.Core`).
  - Проверка прав доступа через `polkit` (изменение политик разрешено только владельцу с валидной аутентификацией).
  - Ведение неизменяемого бинарного журнала аудита (`/var/log/archuvos/audit.wal`) с фиксацией попыток скрытого доступа приложений к закрытым каналам.

### 3.2 `archuvos-capsuled` (Подсистема песочниц «Закрытая территория»)

Каждое пользовательское приложение запускается через утилиту-обертку `archuvos-run <app-name>`, которая конфигурирует и разворачивает изолированное пространство **UVOS Capsule**:

1. **Изоляция пространств имен (Linux Namespaces):**
   - `CLONE_NEWNS` — изолированная точка монтирования VFS.
   - `CLONE_NEWNET` — сетевой неймспейс отключен полностью в режиме *Стерильно*, либо подключен к veth-паре под контролем eBPF.
   - `CLONE_NEWPID` / `CLONE_NEWIPC` — приложение видит только свои процессы и изолированную память IPC.
   - `CLONE_NEWUTS` — подмена имени хоста на детерминированное `archuvos-capsule`.

2. **Маскирование и подмена системных узлов (VFS Overlays):**
   - `/etc/machine-id` подменяется на эфемерный случайный UUID (per-app / per-session), предотвращая аппаратный фингерпринтинг.
   - `/sys/class/power_supply` закрывается пустой монтировкой `tmpfs`, либо подставляется статический узел (состояние: AC Connected, 100%, 0 mV колебаний).
   - `/proc/cpuinfo` санитизируется (скрываются серийные номера и специфичные CPU stepping/microcode ID).

3. **Файловый периметр (Landlock LSM + Bubblewrap):**
   - Доступ на чтение ограничен системным деревом `/usr` (read-only).
   - Доступ на запись разрешен исключительно в изолированный каталог приложения `~/.var/app/<app-name>/`.
   - Домашний каталог `~` (включая `~/.ssh`, `~/.gnupg`, `~/.config`) физически отсутствует в VFS капсулы, пока пользователь явно не выберет файл через XDG Desktop Portal.

4. **Огрубление таймингов и защита от сайд-ченнелов (Time Namespaces + TSC Interception):**
   - **Time Namespaces (`CLONE_NEWTIME`):** Изоляция системных часов на уровне ядра (Linux 5.6+) в связке с Bubblewrap (`bwrap --unshare-time`). Для капсулы настраивается сдвиг в `/proc/self/timens_offsets` для `CLOCK_MONOTONIC` и `CLOCK_BOOTTIME`.
   - **Перехват инструкций TSC (`prctl(PR_SET_TSC, PR_TSC_SIGSEGV)`):** Блокирует прямое чтение процессорных тактов инструкциями `RDTSC` / `RDTSCP` на x86_64 из непривилегированного кода. При попытке выполнения инструкции ядро генерирует `SIGSEGV`, который перехватывается архитектурой капсулы с возвратом квантованного огрубленного значения. Это делает невозможными высокоточные microsecond cache-timing атаки (Spectre v1/v2, FLUSH+RELOAD, аудио/видео джиттер-фингерпринтинг).
   - **seccomp-bpf фильтр:** Перехват и квантование системных вызовов `clock_gettime` и `clock_gettime64` до гранулярности 1000 мс (1 секунда).
   - **Отказ от ненадежного `LD_PRELOAD`:** Аппаратная и уровневая изоляция ядра предотвращает обход таймеров статически скомпилированными бинарниками (Go, Rust musl, C static) или прямыми ассемблерными syscalls.

5. **Обязательный контроль запуска и защита от обхода (Enforced Capsule Launch):**
   - **Симлинки-перехватчики в `/usr/local/bin`:** Каталог `/usr/local/bin` имеет наивысший приоритет в системном `$PATH`. Демон автоматически генерирует симлинки-перехватчики для всех установленных пользовательских приложений, перенаправляющие вызовы на `archuvos-run`.
   - **Сессионный защитный cgroup-каркас:** Вся пользовательская сессия помещается в корневую cgroup v2 (`/sys/fs/cgroup/archuvos/user-session`) с прикрепленным eBPF-фильтром `BPF_PROG_TYPE_CGROUP_SOCK_ADDR`. Любой сокет или сетевой запрос, порожденный процессом вне явно авторизованной подгруппы капсулы `/sys/fs/cgroup/archuvos/capsules/*`, безусловно сбрасывается ядром (`ENETUNREACH`). Даже прямой запуск бинарника по абсолютному пути (например, `/usr/bin/curl`) из консоли или скрипта остается полностью изолированным от сети и файловой системы.
   - **Интеграция с `.desktop`-файлами:** Перехват запуска через системные `.desktop`-файлы: генерация оберток `archuvos-run` в приоритетном каталоге `/usr/local/share/applications/`.

6. **Изоляция D-Bus шины (xdg-dbus-proxy & Polkit):**
   - **Полная изоляция сокетов хоста:** Сокеты системной и пользовательской шин (`/run/user/$UID/bus`, `/run/dbus/system_bus_socket`) физически исключены из точек монтирования капсулы.
   - **Фильтрующий прокси `xdg-dbus-proxy`:** Внутрь песочницы пробрасывается исключительно изолированный прокси-сокет, жестко ограничивающий доступный перечень шин только базовыми порталами XDG (FileChooser, OpenURI). Интерфейсы `org.archuvos.*` полностью замаскированы и недоступны из капсулы.
   - **Мандатная авторизация Polkit:** На стороне системного демона `archuvos-cored` каждый вызов привилегированных методов (включая `SetChannelState`, `SetVoltageOffset`) принудительно валидируется через Polkit (действие `org.archuvos.shield.modify`). Прямой вызов или вызов от неавторизованного субъекта отклоняется с ошибкой `org.freedesktop.DBus.Error.AccessDenied`.

### 3.3 `archuvos-netgovd` (Сетевой регулятор eBPF + Loopback DNS Resolver)

- **Тип:** Низкоуровневый системный фильтр трафика per-app.
- **Технологический стек:** eBPF (`cgroup_skb/ingress`, `cgroup_skb/egress`, `sock_addr`) + петлевой DNS-резолвер (`127.0.0.53`).
- **Защита от обхода через DoH (DNS-over-HTTPS) и DoT (DNS-over-TLS):**
  - eBPF-фильтр на сокетах безусловно блокирует исходящие пакеты на порт 853 (DoT), а также прямое обращение по IP к известным публичным DoH-резолверам на порту 443.
  - В режиме `WHITELIST` исходящий трафик на 443 порт разрешен **исключительно** на IP-адреса, которые были успешно разрезолвлены локальным петлевым DNS-прокси (`127.0.0.53`) в рамках одобренных доменов. Прямая попытка приложения инициировать TLS-сессию с произвольным IP-адресом (включая скрытые DoH-эндпоинты) мгновенно сбрасывается ядром на уровне `connect()`.
  - Каждой капсуле монтируется синтетический `/etc/resolv.conf`, принудительно направляющий все запросы на `127.0.0.53`.
- **Режимы работы для каждого приложения:**
  1. `CLOSED` (По умолчанию / Стерильно): Любой исходящий сокет мгновенно блокируется eBPF (`BPF_DROP`), возвращая `ENETUNREACH`. Приложение изолировано от внешнего мира.
  2. `WHITELIST` (Белый список FQDN):
     - Петлевой резолвер `archuvos-netgovd` сверяет запрашиваемое доменное имя со списком разрешенных хостов капсулы.
     - При совпадении IP-адрес заносится в динамическую eBPF hash-map `allowed_ips_map` со временем жизни TTL.
     - Исходящие TCP/UDP пакеты пропускаются ядром **только** на IP-адреса из `allowed_ips_map`. Прямые обращения по IP-адресам в обход DNS немедленно дропаются.
  3. `OPEN`: Полный доступ с подсчетом переданных байт в реальном времени.
- **Телеметрия трафика:** Демон транслирует скорость Rx/Tx с частотой 20 Гц в D-Bus для управления стрелочным индикатором скорости сети на панели задач.

### 3.4 `archuvos-undervoltd` (Аппаратный контроллер питания и андервольтинга)

- **Назначение:** Реализация концепции **UnderVolt** — аппаратная оптимизация энергопотребления, температур и стабильности.
- **Поддерживаемое железо:**
  - **Intel Core (6th Gen – 14th Gen):** Управление через MSR-регистры (`MSR_OC_MAILBOX` 0x150) смещениями CPU Core, Processor Graphics (GT), Cache, System Agent.
  - **AMD Ryzen (Zen 2 – Zen 5):** Интеграция с драйвером `amd_pstate`, Curve Optimizer через `ryzen_smu` / SMU mailbox.
  - **GPU (AMD / Intel / NVIDIA):** Управление P-State кривыми через `sysfs` (`amdgpu_pm_info`, `intel_gpu_frequency`).
- **Защита от Silent Data Corruption (SDC) и целостность вычислений:**
  - При чрезмерном андервольтинге процессор может совершать скрытые микроошибки вычислений (SDC — Silent Data Corruption), необратимо повреждающие кэш, память и файловые системы.
  - **Безопасные жесткие лимиты (Hard Bounds):**
    - Предельное смещение жестко ограничено в коде демона безопасным диапазоном **-30...-50 mV** для CPU Core и не более **-30 mV** для Cache/Ring.
    - Опасные значения (например, -120 mV) программно запрещены.
    - Полная блокировка любого овервольтинга (положительное смещение заблокировано).
  - **Интегрированный стресс-тест целостности памяти и кэша:** Перед фиксацией любого нового профиля смещения демон в изолированном потоке выполняет быстрый алгоритмический стресс-тест AVX2/SHA256 (500 мс) с проверкой контрольных сумм.
  - **Мониторинг MCE (Machine Check Exceptions):** Демон опрашивает подсистему ядра `rasdaemon` / `/dev/mcelog`. При обнаружении первой же скорректированной аппаратной ошибки кэша L1/L2/L3 смещение немедленно откатывается на безопасный заводской уровень (+15 mV откат).
- **Проверка статуса Kernel Lockdown:**
  - Демон при старте опрашивает узел `/sys/kernel/security/lockdown`.
  - Если активен режим ядра `[integrity]` или `[confidentiality]` (типично для `linux-hardened` или систем с включенным UEFI Secure Boot), прямая запись в MSR 0x150 блокируется ядром (`CAP_SYS_RAWIO denied`).
  - В этом случае `archuvos-undervoltd` фиксирует предупреждение в журнале, отключает запись в MSR и корректно переходит в **пассивный режим телеметрии** через стандартные безопасные узлы `hwmon` и `powercap`, не вызывая аварийных сбоев демона.
- **Сбор телеметрии в реальном времени:**
  - Вольтаж ядра (Vcore) — опрос `hwmon` / MSR с частотой 10 Гц.
  - Потребляемая мощность (CPU Package Power) через RAPL (`/sys/class/powercap/intel-rapl`).
  - Температуры ядер и скорость вращения кулеров (RPM).
- **Автоматический адаптивный регулятор (`Adaptive Governor`):**
  - Режим по умолчанию: система сама выбирает оптимальный уровень андервольтинга в зависимости от температурного баланса и нагрузки (динамически от -20 mV до -50 mV).
  - **Hardware Fail-safe Protection:** Сторожевой таймер (Watchdog). Если при изменении параметров напряжения происходит зависание или kernel crash, при следующей перезагрузке параметры автоматически сбрасываются в безопасный заводской профиль.

## 4. Спецификация D-Bus API

Системная шина: `org.archuvos`  
Путь к объектам: `/org/archuvos/*`

### 4.1 Интерфейс `org.archuvos.Shield` (Управление щитком разрешений)

```xml
<interface name="org.archuvos.Shield">
  <!-- Получить список всех установленных капсул и их состояний -->
  <method name="GetAppPolicies">
    <arg type="s" name="filter" direction="in"/>
    <arg type="a{sa{sv}}" name="policies" direction="out"/>
  </method>

  <!-- Переключить тумблер канала для приложения -->
  <!-- channel: "network", "camera", "mic", "time_sanitize", "battery_mask", "storage" -->
  <method name="SetChannelState">
    <arg type="s" name="app_id" direction="in"/>
    <arg type="s" name="channel" direction="in"/>
    <arg type="b" name="enabled" direction="in"/>
    <arg type="b" name="success" direction="out"/>
  </method>

  <!-- Сигнал попытки несанкционированного доступа (для индикатора на приборном щитке) -->
  <signal name="AccessAttemptBlocked">
    <arg type="s" name="app_id"/>
    <arg type="s" name="channel"/>
    <arg type="t" name="timestamp_ms"/>
  </signal>
</interface>
```

### 4.2 Интерфейс `org.archuvos.Hardware` (Телеметрия и андервольтинг)

```xml
<interface name="org.archuvos.Hardware">
  <!-- Получение мгновенных метрик для отрисовки приборов М4200 -->
  <method name="GetTelemetry">
    <arg type="d" name="vcore_volts" direction="out"/>
    <arg type="d" name="pkg_power_watts" direction="out"/>
    <arg type="d" name="temp_celsius" direction="out"/>
    <arg type="u" name="fan_rpm" direction="out"/>
  </method>

  <!-- Установка профиля питания: 0=AUTO, 1=AIRGAP, 2=ECO, 3=BALANCED, 4=OVERDRIVE -->
  <method name="SetPowerProfile">
    <arg type="u" name="profile_id" direction="in"/>
    <arg type="b" name="success" direction="out"/>
  </method>

  <!-- Смещение вольтажа (защищено Polkit, только ручной режим) -->
  <method name="SetVoltageOffset">
    <arg type="s" name="domain" direction="in"/> <!-- "cpu_core", "cpu_cache", "gpu" -->
    <arg type="i" name="offset_mv" direction="in"/> <!-- отрицательное число, например -65 -->
    <arg type="b" name="success" direction="out"/>
  </method>
</interface>
```

## 5. Конфигурационные файлы и размещение в ФС

Все конфигурации ArchUVOS хранятся в строгом формате TOML в директории `/etc/archuvos/`:

```
/etc/archuvos/
├── core.toml               # Общие настройки супервизора и журналов
├── hardware.toml           # Настройки вольтажа, лимиты TDP, кривые вентиляторов
├── network.toml            # Общие правила сети и списки разрешенных DNS
└── capsules.d/             # Индивидуальные профили песочниц приложений
    ├── default.toml        # Шаблон по умолчанию (Zero-Trust, всё закрыто)
    ├── firefox.toml        # Профиль браузера
    ├── telegram.toml       # Профиль мессенджера
    └── terminal.toml       # Профиль доверенного терминала
```

### Пример `/etc/archuvos/capsules.d/default.toml`:
```toml
[capsule]
name = "default_zero_trust"
version = "1.0"

[sandbox]
isolate_network = true
isolate_pid = true
isolate_ipc = true
sanitize_time = true
fake_machine_id = true
mask_battery = true

[filesystem]
read_only_paths = ["/usr", "/lib", "/bin", "/etc/ssl"]
bind_app_data = true # Создает ~/.var/app/{app_id}
home_access = "none" # "none", "portal_only", "full"

[network]
mode = "DROP" # "DROP", "WHITELIST", "ALLOW"
allowed_domains = []
```

## 6. Интеграция с Arch Linux и Pacman

Для обеспечения бесшовного опыта пользователя в Arch Linux фоновый стек интегрируется на уровне пакетного менеджера:

1. **Pacman Hook (`/etc/pacman.d/hooks/95-archuvos-capsule.hook`):**
   При установке любого пакета, содержащего `.desktop`-файл в `/usr/share/applications/`, хук автоматически:
   - Генерирует дефолтный профиль капсулы в `/etc/archuvos/capsules.d/<pkgname>.toml`.
   - Проверяет безопасность бинарников через Landlock-валидатор.
   - Регистрирует приложение в базе Контрольного щитка с состоянием **«ВСЁ ЗАКРЫТО»**.

2. **Systemd Services:**
   - `archuvos-core.service` — запускается на этапе `sysinit.target`.
   - `archuvos-undervolt.service` — применяется до входа в графическую среду.
   - `archuvos-netgov.service` — инициализирует eBPF-программы при старте сети.

## 7. Безопасность и отказоустойчивость (Hardware & Sandbox Fail-Safe)

1. **Защита кремния и целостности данных от некорректного вольтажа:**
   - Предельное аппаратное смещение жестко ограничено в коде демона (Hard Limit: безопасный коридор от -30 до -50 mV для CPU Core, не более -30 mV для Cache/Ring) для полного исключения риска Silent Data Corruption (SDC).
   - Предохранительный замок: попытка выставить положительное смещение (overvolting) полностью заблокирована на аппаратном уровне ядра драйвера.
   - Проверка статуса `/sys/kernel/security/lockdown` для предотвращения несанкционированного доступа к MSR в защищенных конфигурациях ядра.
2. **Аварийный сброс (Safe Fallback Kernel Boot):**
   - Добавление опции ядра `archuvos.safe_mode=1` при загрузке GRUB/systemd-boot отключает все смещения напряжений и сбрасывает сетевые фильтры в режим открытого доступа для восстановления системы.
3. **Целостность изоляции:**
   - Даже если скомпрометированный бинарник получает выполнение RCE в песочнице, отсутствие `CAP_SYS_ADMIN`, изоляция монтирований и Landlock делают побег из капсулы математически невозможным без использования 0-day уязвимости ядра Linux.
